## P0 - Required before the feature works

### 1. Verify (and if needed, refresh) the dev Azure SP credentials

**Pre-flight check - 10 seconds.** Run from the shell you normally
use for backend scripts:

```powershell
cd backend
$env:AZURE_STORAGE_ACCOUNT_NAME="stthesrilathaartsdev"
npx ts-node scripts/seedAdmin.ts   # read-only, no data written
```

- ✅ If the script succeeds → SP creds are good for the
  `DefaultAzureCredential` path the migration + backfill rely on.
  **Skip the rest of §1.**
- ❌ If it fails with `AADSTS7000215` (*Invalid client secret*),
  the value in the `AZURE_CLIENT_SECRET` env var is stale and the
  steps below apply.

**Background - why this check matters.** The `az` CLI and the
deploy script use az's local token cache (seeded by `az login`),
which keeps working even when the SP env-var secret is stale.
`DefaultAzureCredential` instantiated inside our Node scripts goes
straight to `EnvironmentCredential` and reads the env var, so it
fails noisily where `az` doesn't. The pre-flight covers the
specific code path the scripts in §3 and §4 use.

**Refresh procedure (only if the pre-flight failed):**

- Generate a new client secret for the dev SP (App registration
  `e762146a-3696-4a42-bd7e-b3160279be1e`) in Entra ID → App
  registrations → Certificates & secrets.
- Update the local PowerShell profile / Windows User env vars with
  the new `AZURE_CLIENT_ID` / `AZURE_CLIENT_SECRET` /
  `AZURE_TENANT_ID`. (If you only set them inside your PowerShell
  session, child processes like Node subprocesses may not inherit
  - set them as Windows User Environment Variables for stable
  cross-shell inheritance.)
- Re-run the pre-flight check above; it should now pass.

## P2 - Follow-ups worth doing soon

### A. Public-URL hardening for invoices

`/invoices/{id}.pdf` is reachable without auth (WhatsApp Cloud
needs to fetch it server-to-server). IDs are 14-digit timestamps
which are casually guessable. Options when there's time:

- Add an HMAC token to the URL: `/invoices/{id}.pdf?t=<hex>`,
  validated by `invoiceDownload.ts`. Token is included in the
  branded URL sent over WhatsApp + email + admin.
- Or move the path behind the auth cookie when accessed from the
  web app (separate route for WhatsApp's bot fetch).

### B. Refund notification path

`payments.ts` still enqueues `refund_processed` messages, but the
queue consumer doesn't handle that template yet. Add a
`refund_processed` handler in `notificationsQueue.ts` + matching
email template when refunds get the same treatment.

### C. Email log viewer in admin

`GET /api/admin/orders/{id}/email-logs` is wired but the admin UI
doesn't have a viewer yet. Add a modal or expandable section on the
order detail page that lists each send attempt.

### D. Remove `enqueueNotification` call sites that have no consumer

Audit any remaining `enqueueNotification` calls with `templateKey`
values that aren't in `notificationsQueue.ts`'s switch. Today
that's `refund_processed` and any future ones. Either implement
the handler or stop enqueueing.

### E. Move SMTP_PASS to Key Vault

Currently set as a plain Function App application setting. Wrap
in a Key Vault reference so secret rotation doesn't require a
config edit on the Function App.

### F. Tests

No unit tests landed for:

- `services/orderNumber.ts` - uniqueness retry behaviour
- `services/email.ts` - transporter wiring (can stub nodemailer)
- `services/emailTemplates/orderConfirmation.ts` - snapshot test

- `functions/notificationsQueue.ts` - channel routing

Worth adding before this surface grows.

### G. Admin reply UX in the WhatsApp inbox

Today's inbox is view-only. Phase 2:

- Template picker for routine messages (shipping update, refund
  ack) - works outside WhatsApp's 24-hour window.
- Free-form reply textarea - only enabled when the most recent
  inbound message is within the last 24 hours (WhatsApp policy).
- Reuse the existing `sendTemplateMessage` for templates; add a
  `sendTextMessage` helper for the free-form path. Both must write
  outbound rows + bump the conversation rollup identically to the
  system-driven sends.

### H. Customer-name backfill on conversations

`whatsappConversations.customerName` is populated from Meta's
contact profile on first inbound, OR from the order's
`customerName` on outbound. For threads that started with an
inbound message before we'd ever seen the customer, the name field
can be empty. A one-shot script that joins `whatsappConversations`
against `orders` by phone and fills in the missing names would
make the inbox more usable.

## Reference

- Order #/Invoice # format: `YYYYMMDDHHMMSSFF` (IST), 16 digits.
  `FF` = first two digits of the zero-padded 3-digit millisecond value
  at order creation (e.g. `.789 → 78`, `.050 → 05`).
- Branded URL: `https://www.srilatha.art/invoices/{InvoiceNumber}.pdf`
  → SWA rewrite → `/api/invoices/{file}` → blob stream.
- Single source of truth: PDF lives at
  `{INVOICE_CONTAINER}/{InvoiceNumber}.pdf`. Every channel reads
  from there; nothing regenerates downstream.
- WhatsApp template: `order_confirmation_new_artwork`,
  `{{1}}=customerName`, `{{2}}=orderId`, DOCUMENT header.
- Notifications queue: `notifications-out` (env
  `NOTIFICATIONS_QUEUE_NAME`). Poison queue:
  `notifications-out-poison`.
- Inbound webhook URL (paste into Meta):
  - DEV: `https://func-thesrilathaarts-dev.azurewebsites.net/api/webhooks/whatsapp`
  - PRD: `https://func-thesrilathaarts-prd.azurewebsites.net/api/webhooks/whatsapp`
- Admin Conversation Center: `/admin/whatsapp` (linked from the
  admin sidebar between "Reviews" and "Coupons").
- New Azure Table Storage tables (provisioned by
  `Deploy-Infrastructure.ps1` on re-run):
  - `emailLogs` - per-attempt SMTP delivery log
    (PK = orderId, RK = ISO-timestamp_attempt).
  - `whatsappMessages` - append-only log of every WhatsApp message
    in either direction (PK = phone E.164 no '+', RK =
    `{timestamp}_{outbound|inbound}_{wamid}`).
  - `whatsappConversations` - per-phone rollup powering the inbox
    left rail (PK = `conv`, RK = phone).
