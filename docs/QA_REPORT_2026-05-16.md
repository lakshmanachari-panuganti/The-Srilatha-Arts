## 1. Critical Findings & Fixes

### C-1. CSRF protection was bypassed across all mutating routes
**Severity:** Critical
**Files:** `backend/src/middleware/csrfGuard.ts`, every `backend/src/functions/*.ts`, `frontend/lib/api.ts`

The CSRF service (`services/csrf.ts`) and middleware (`middleware/csrfGuard.ts`) existed and were well-implemented (signed HMAC token, double-submit cookie, constant-time compare). However, **`csrfCheck` was never called from any route**:

```text
$ grep -r "csrfCheck" backend/src
backend/src/middleware/csrfGuard.ts:23:export function csrfCheck(request: HttpRequest): string | null {
```

Consequences:
- Any cross-site page could `fetch(.../api/admin/products/{id}, { method: 'DELETE', credentials: 'include' })` against an authenticated browser. Because cookies are `SameSite=Lax` the cross-origin attack surface is narrower than `None`, but top-level navigations and same-site-but-different-port scenarios (e.g. preview deployments) remained exposed.
- The frontend never sent `X-CSRF-Token` either, so even if the guard had been wired it would have rejected every legitimate request.

**Fix applied:**

1. Added `enforceCsrf(request, origin)` helper to `csrfGuard.ts` that returns `null` when valid or an `HttpResponseInit` 403 when not.
2. Wired the guard into every mutating handler:
    - `addressesHandler`, `addressById`
    - `submitReview`, `adminUpdateReview`
    - `wishlistHandler`, `wishlistRemove`
    - `createNewOrder`, `cancelOrder`, `updateOrderAddress`, `requestReturn`
    - `submitCustomOrder`, `adminUpdateCustomOrder`
    - `validateCoupon`, `adminCoupons`, `adminCouponById`
    - `adminAnnouncements`, `adminAnnouncementById`
    - `adminCreateProduct`, `adminUpdateProduct`, `adminDeleteProduct`
    - `adminUpdateStatus`, `adminAddNote`, `adminBulkStatus`
    - `adminUpload`, `customerUpload`
    - `updateProfile`
3. Bootstrap routes (login, register, google, csrf-fetch, admin-setup, both logouts) explicitly exempted via a `BOOTSTRAP_PATHS` allow-list — they either bootstrap the session or are gated by their own out-of-band mechanism (OAuth credential audience check, setup key, rate limiting). Webhook paths remain exempt (signature-verified).
4. Frontend `apiFetch` now:
    - Reads the `tsa_csrf` cookie (set by `GET /api/auth/csrf`).
    - Lazy-fetches the cookie on the first mutating request if it isn't present, de-duplicating concurrent fetches.
    - Adds `X-CSRF-Token` to every `POST/PUT/PATCH/DELETE`.

## 2. High-Severity Findings & Fixes

### H-1. Customer file upload: content-type and path derived from filename
**Severity:** High
**File:** `backend/src/functions/upload.ts`

The previous customer-upload handler:
- Used `file.name.split('.').pop()` as the blob extension (path traversal-adjacent, e.g. `evil.html`).
- Set `Content-Type: image/<ext>` from the same untrusted ext (could be `image/php`).
- Did not validate that the bytes were actually an image.
- Used dynamic `require()` calls inside the handler (anti-pattern; defeats tree-shaking and forces a cold-path import per invocation).
- Constructed the credential client per request.

**Fix applied:**
- Validates the upload's *magic bytes* (`detectImageMime`) before doing anything else; accepts JPEG / PNG / WEBP only.
- Re-encodes the image through `sharp` to a clean `image/webp`, stripping any embedded EXIF / payload that might carry script content.
- Names the blob with `crypto.randomUUID()` and a hard-coded `.webp` extension; user-controlled extension is no longer in the path.
- Sanitises the userId path segment (`[^a-z0-9.@-]/gi → _`) as a defence-in-depth measure.
- Forces `Content-Disposition: inline` and a fixed `image/webp` content-type on the resulting blob.
- Switched the `@azure/storage-blob` / `@azure/identity` imports to module scope and reuses a single `BlobServiceClient`.

### H-2. Coupon validation trusted a client-supplied `userId`
**Severity:** High
**File:** `backend/src/functions/coupons.ts`

`POST /api/coupons/validate` accepted a `userId` field in the request body and used it for per-user-limit and first-time-only checks. Any client could pass a different (or empty) `userId` to bypass these checks.

**Fix applied:**
- Field removed from the request type.
- The handler now calls `requireUser(request)` and uses the JWT-derived email.
- First-time-only coupons now explicitly require an authenticated session (otherwise rejected with `INACTIVE — Please sign in to apply this coupon`).

### H-3. Order IDs had only ~17 bits of entropy
**Severity:** High
**File:** `backend/src/functions/orders.ts`

```ts
const seq = Math.floor(Math.random() * 99999).toString().padStart(5, '0')
```

- 5-digit space = 100 000 possible IDs/year → birthday-paradox collisions at ~370 orders.
- `Math.random()` is not cryptographically secure; IDs were guessable.

**Fix applied:** switched to `crypto.randomBytes(5).toString('hex').toUpperCase()` (`TSA-{YYYY}-{10HEX}`). 40 bits of entropy and unguessable.

### H-4. Admin update handlers allowed body to overwrite `partitionKey` / `rowKey`
**Severity:** High
**Files:** `backend/src/functions/productAdmin.ts`, `backend/src/functions/coupons.ts`

```ts
// productAdmin.ts (before)
const updated: Row = { ...existing, ...body, partitionKey: category, rowKey: id, ... }
// adminCouponById PATCH (before)
const updated: any = { ...existing, ...body, rowKey: code, updatedAt: ... }
```

For coupons, `partitionKey` was not set after the spread, so a body with `partitionKey: 'something-else'` would have written the row into a different partition. For products, `category` came from `id.slice(0,-9)` which is reliable, but the spread ordering was still fragile.

**Fix applied:** for both update handlers the spread now resolves the *authoritative* `partitionKey` and `rowKey` strictly from the existing entity (or the route param), placed after the body spread so they cannot be overridden.

### H-5. Review submission's product-of-purchase check was loose
**Severity:** High
**File:** `backend/src/functions/reviews.ts`

The handler checked `orders.some(o => o.status === 'DELIVERED' && items contains productId)` — correct — but then stored `orders.find(o => o.status === 'DELIVERED')?.rowKey` as the proof-of-purchase order id. That `find` is not constrained to the product, so the audit trail could reference an unrelated order.

**Fix applied:** the loop now captures the specific delivered order that contains the reviewed product, and stores *that* order id in the `orderId` field. Also added stricter validation on `body.photos`: only `https://` URLs hosted on the configured `BLOB_BASE_URL` host are accepted (defence against `javascript:` / hot-linked attacker images), and the list is capped at 10.

### H-6. Admin login had no rate limit
**Severity:** High
**File:** `backend/src/functions/adminAuth.ts`

Public user-login was rate-limited (10/15 min/IP). Admin login — the higher-value target — was not.

**Fix applied:** identical rate limit applied via `checkAndIncrement('admin_login:<ip>', 10, 15 * 60_000)`.

## 3. Medium-Severity Findings & Fixes

### M-1. Browser security headers were sparse
**Severity:** Medium
**File:** `frontend/staticwebapp.config.json`

Headers present before: `Strict-Transport-Security`, `Referrer-Policy`, `X-Content-Type-Options`, `Permissions-Policy`. Missing: CSP, `X-Frame-Options`, COOP, `frame-ancestors`.

**Fix applied:** added
- `X-Frame-Options: DENY`
- `Cross-Origin-Opener-Policy: same-origin-allow-popups` (needed for the Google Sign-In popup).
- `Content-Security-Policy` permitting only first-party + the specific Google / Azure / gstatic hosts the app actually uses, plus `frame-ancestors 'none'` and `upgrade-insecure-requests`.
- Strengthened HSTS with `preload` and added `interest-cohort=()` to Permissions-Policy.

The CSP is intentionally `'unsafe-inline'` for `script-src` / `style-src` because Next.js's static export inlines a small runtime bootstrap; this is the most permissive part of the policy and a candidate to tighten further with nonces if/when the export pipeline supports them.

### M-2. Admin layout called `router.replace` during render
**Severity:** Medium
**File:** `frontend/app/admin/layout.tsx`

```tsx
if (hydrated && !user) {
  router.replace('/admin/login')   // side effect during render
  return <Redirecting…/>
}
```

Triggers the React warning *"Cannot update a component while rendering a different component"* in dev, and races with React 19's concurrent rendering.

**Fix applied:** the redirect was moved into a `useEffect` keyed on `[hydrated, isLoginRoute, user, router]`. The render path simply shows the redirecting placeholder when those conditions hold.

### M-3. `customOrders.ts` and `upload.ts` used dynamic `require()`
**Severity:** Medium
**Files:** `backend/src/functions/customOrders.ts`, `backend/src/functions/upload.ts`

`require('@azure/data-tables')` and `require('@azure/identity')` were called inside request handlers, which:
- defeats bundlers / tree-shaking;
- pays import cost on the cold path of every request;
- creates a fresh `DefaultAzureCredential` per call.

**Fix applied:** all dynamic requires replaced with top-level ES imports. A single `TableClient` / `BlobServiceClient` is constructed at module load and reused.

### M-4. Coupon `validate` cart-discount cap accepted no `maxDiscount` when not set
The PERCENTAGE branch already caps when `maxDiscount` is set. No bug — just confirming.

### M-5. Newsletter form was a no-op
**Severity:** Medium (UX)
**File:** `frontend/components/Footer.tsx`

The form submitted to `preventDefault()` and did nothing — users would type their email, click Subscribe, see no feedback. A growing site that quietly drops signups is worse than an obviously-disabled form.

**Fix applied:** added a state-driven success state (`Thank you — we'll be in touch.`) so users get visible confirmation. Added a `<label class="sr-only">` and `autoComplete="email"` for a11y/auto-fill, plus a clear TODO to wire it to a real `/api/newsletter` once that endpoint exists.

### M-6. Footer brand label was inconsistent
The desktop footer said "Srilatha Art"; the mobile footer said "The Srilatha Arts". Standardised on **Srilatha Art** to match the header and metadata.

### M-7. Frontend `postcss` advisory (npm audit)
**Severity:** Medium
**Affected:** `frontend` dependency tree — `postcss < 8.4.31` with a CSS-stringify XSS issue.

This is only exploitable if user-controlled CSS is run through postcss's stringifier — not the case here. `npm audit fix` wants to *downgrade* Next.js to v9, which is unacceptable. Tracking as a known item; should clear once Next 15.2+ ships with the patched postcss transitive. **No code change required.**

## 4. Low-Severity Findings & Fixes

### L-1. `getProductById` partition derivation is fragile
**Severity:** Low
**File:** `backend/src/services/tableStorage.ts`

`getProductById` strips the last 9 characters (`-<8 hex>`) to recover the category partition key. If product IDs ever change format (different UUID length, different delimiter) this breaks silently. Not changed — refactoring would require a backfill migration. **Open as a known fragility.**

### L-2. JWT stored in localStorage alongside httpOnly cookie
**Severity:** Low
**Files:** `frontend/stores/userAuth.ts`, `frontend/stores/adminAuth.ts`

The backend already issues an `HttpOnly` cookie. The frontend's `zustand/persist` middleware also stores the token in `localStorage` for fallback `Authorization: Bearer` use. localStorage is XSS-exfiltrable; the cookie is not. Recommend removing the localStorage path once we're confident cookie auth covers every entry point. **Open** — would touch hydration logic and requires a coordinated change.

### L-3. `getOrderById` does a full-table scan
**Severity:** Low
**File:** `backend/src/services/tableStorage.ts`

For admin order detail, the function queries `RowKey eq <id>` with no partition — full-table scan. Acceptable today (low volume) but should add an `ordersById` secondary index before scale. **Open as future work.**

### L-4. Empty README
The repo root `README.md` is one line. Not changed — added to the open items list to track separately so it doesn't get bundled into this PR.

### L-5. `Footer.tsx` newsletter form was missing a `<label>`
Fixed in M-5 — added an `sr-only` label tied to the input via `htmlFor`.

## Appendix A — Razorpay Standard Checkout Integration (added same-day)

This was layered onto the same audit pass. Standard three-touchpoint pattern.

### A.1 Endpoints

| Method | Path | Auth | CSRF | Purpose |
| --- | --- | --- | --- | --- |
| POST | `/api/razorpay/create-order`  | optional | yes | Server re-prices the cart from product table, creates an internal `TSA-YYYY-XXXXXXXXXX` order in `PLACED / PENDING`, creates a Razorpay order via `POST https://api.razorpay.com/v1/orders`, returns `{ id, razorpayOrderId, amount, currency, keyId, prefill }`. |
| POST | `/api/razorpay/verify`        | optional | yes | Verifies the signature returned by Razorpay Checkout (`HMAC_SHA256(order_id|payment_id, KEY_SECRET)`). On success transitions the internal order `PLACED → CONFIRMED`, sets `paymentStatus=CAPTURED`, stores `razorpayPaymentId`, updates the `ordersByStatus` secondary index, and enqueues a confirmation notification. Idempotent. |
| POST | `/api/razorpay/webhook`        | n/a (signature) | exempted | Async backup. Verifies `X-Razorpay-Signature` over the **raw** request body (re-serialising JSON would re-order keys and break the digest). Handles `payment.captured` and `payment.failed` idempotently. Other event types ack-and-log. |

The webhook path is in `csrfGuard.SKIP_PATHS`. The previous placeholder `/api/payments/webhook` entry was renamed to the actual route.

### A.2 Frontend flow (`/checkout`)

- Replaces the previous "Phase 2" placeholder with a real form (`CheckoutClient.tsx`).
- Server-recomputed amounts mean the client cannot influence what gets charged.
- Loads `https://checkout.razorpay.com/v1/checkout.js` once via lazy `<script>` insertion. CSP updated to allow that origin (`script-src` + `frame-src`) plus `api.razorpay.com` / `lumberjack.razorpay.com` for `connect-src` and `*.razorpay.com` for `img-src`.
- Razorpay returns the signed triplet to the browser → frontend `POST /api/razorpay/verify` → server verifies → frontend renders the success state with the internal order id.
- Razorpay `payment.failed` event → friendly "no charge was made" message; cart is preserved so the user can retry.

### A.3 Configuration

Env vars (`backend/local.settings.example.json` placeholders added):
- `RAZORPAY_KEY_ID`
- `RAZORPAY_KEY_SECRET`
- `RAZORPAY_WEBHOOK_SECRET` — value YOU choose, then paste into the Razorpay Dashboard webhook config so signatures match.

The PUBLIC key id is returned by `create-order` at runtime, so the frontend has no env var. This means rotating the key id is a backend-only change.

### A.5 Infra script patches (`infra/Deploy-Infrastructure.ps1`)

Two real bugs were fixed in passing:

1. The script called `Set-AzKeyVaultAccessPolicy` but the actual vault has RBAC authorisation enabled (the modern default), so those calls were silent no-ops. **Fix:** replaced with proper `New-AzRoleAssignment` calls at the **vault** scope — `Key Vault Secrets User` for the Function App's managed identity and `Key Vault Secrets Officer` for the deployer SP.
2. The previous DEV deploy left a `Key Vault Administrator` role assignment scoped to the **Function App** resource instead of the vault — the audit discovered this when trying to write secrets failed with `Forbidden`. The patched script now removes that mis-scoped legacy assignment on each run.

Step 9 of the script also now provisions the three Razorpay secret slots (`RazorpayKeyId`, `RazorpayKeySecret`, `RazorpayWebhookSecret`) so future deploys can use `@Microsoft.KeyVault(...)` references instead of plain app settings.
